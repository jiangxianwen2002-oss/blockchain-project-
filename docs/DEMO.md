# 演示脚本：怎么证明"交易真的发生了"

> 正式演示用 **stage 环境**（默认启动就是它，链上是干净的，从第一单开始）。自己练习时命令前加 `AV_ENV=rehearsal`，练习环境的标签标题会带"[练习]"。下面的地址都是 stage 环境的。

> 给上台演示的同学用。核心原则：**页面上说的每一件事，都能点开 Etherscan 找到对应的链上记录。**
> 老师不需要相信我们的前端，也不需要相信 AI 服务。证据来自以太坊公共节点和 Etherscan。

## 演示前准备（5 分钟）
1. 启动服务（在项目根目录）：
   ```bash
   (cd agent && npm run server &) && cd frontend && npm run dev
   ```
2. **两个窗口左右并排**（投影上最直观）：
   - 左边窄窗口：**助手** http://localhost:5173 ，扮演"员工 / 孩子"
   - 右边宽窗口：**控制台** http://localhost:5174 ，扮演"管理员"，MetaMask 连 Owner 账户
3. 另外准备两个 Etherscan 标签页：
   - **B：外卖合约的 mUSDC 记录** https://sepolia.etherscan.io/token/0x18CaD1a9F7a97F73dA3EbA11779B37F045c8f42A?a=0xAbd934d535418dc79eC837236bd11F274d54d69D
   - **C：AI 代理钱包** https://sepolia.etherscan.io/address/0x9Da8FA6692614E0Aadc9CabC59292A0609Ef73D1
4. 在 **控制台 → 链上对账** 先截一张图，作为"演示前"的余额。

## 为什么这些证据可信（被问到时这样回答）
- **合约源码公开**：每个合约在 Etherscan 上都是"已验证源码"（Contract 标签有绿色对勾），任何人都能确认链上跑的代码就是 GitHub 上的代码。
- **网页的数字不来自我们的服务器**：链上对账和订单凭证是浏览器直接向以太坊公共节点查询的，AI 服务停掉也照样能看。
- **转账从交易回执解码**：订单卡片里的"💸 29 mUSDC：小钱包 → 外卖合约"，是从这笔交易的回执中解码出的 ERC-20 Transfer 事件，和 Etherscan 显示的是同一条数据。
- **被拒绝的也有记录**：被合约拒绝的付款，我们也故意发上链。它会在 Etherscan 上显示为红色的失败交易，原因是合约给出的（例如 MerchantNotAllowed）。

## 演示流程（约 4 分钟）

### ① 买入：AI 点外卖，钱进托管
- 助手 → 点"帮我点个午饭，30 块以内，不要辣"
- 讲解：AI 看了**链上菜单** → 在**外卖合约上下单**（总价由合约算）→ 从小钱包**付款**
- **证据**：
  - 订单小票 → 点"链上凭证"：显示"付款，进入托管：29.00 钱包（金库合约）→ 饭点到·家常小厨"，以及区块号（点区块号跳到交易）
  - 切到标签页 B，刷新：最上面多了一笔 **29 mUSDC，From 金库 To 外卖合约**，和卡片上的哈希一致
  - 控制台 → 链上对账：钱包 −29，外卖合约"托管中" +29，三项校验全部通过

### ② 退款（卖出）：送达前取消
- 助手里说"取消刚才的订单"
- **证据**：凭证里多了"↩️ 退款回小钱包"，标签页 B 刷新后多一笔 **29 mUSDC，From 外卖合约 To 金库**，方向和刚才相反。对账表里小钱包加回 29。

### ③ 超额 → 人审批 → 放款给商家
- 助手里说"给全组 6 个人点奶茶"（90，超过单笔上限 30）→ 小票显示"待审批"
- **自用方式（推荐）**：直接在助手的小票上点「批准并付款」，MetaMask 弹窗签名，聊天里出现"你批准了这笔付款"。
- **管理端方式**：控制台左侧"审批"出现数字角标，右上角弹出提醒 → 点"批准"（MetaMask 签名）。两边状态同步
- **证据**：
  - 卡片变成"已付款 · 钱在合约托管"，凭证里的付款交易就是**你刚才签名的那笔批准交易**
  - 约 40 秒后商家送达；在控制台 → 订单里选中这单，点"确认收货"（或在助手里说"收到了"，或等 3 分钟自动放款）
  - 商家后台自动提现 → 凭证里出现"商家提现：90.00 一点甜·奶茶咖啡 → 商家钱包"
  - 对账表里，"商家钱包（已提现到手）"增加 90

### ④ 诈骗店：AI 被骗了，钱也没出去
- 助手 → 点"试试诈骗店：首单 1 折"
- 讲解：店铺公告里藏了一段写给 AI 的"系统通知"，要求先付 50 元激活费。离线模式的"笨 AI"照做了。
- **证据**：
  - 小票显示"已拦截"，点"失败交易"：Etherscan 上状态是红色的 **Fail**，原因是 **MerchantNotAllowed**；AI 的工作过程会自动展开，标出这家店公告里写给 AI 的指令
  - 点"这家店的收款记录"：诈骗店合约**一笔转账都没有**
  - 标签页 C（AI 代理钱包）里也能看到这笔红色失败交易

### ⑤ 新商家入驻：管理员导入，AI 马上能买
- 讲解：商家已经用 `DeployShop.s.sol` 开了一家「小卖部·便利店」（合约 `0xbEb6…7c65`，已验证源码），但还不在白名单里。
- 先在助手里说"帮我在便利店买瓶可乐"：AI 找不到这家店，因为它不在白名单里。
- 控制台 → 商家白名单 → 添加商家 → 粘贴 `0x96465E99Baf51BE72af31B0FF2eb812EdC1d9426`：五项检查全部通过，下面显示店名、店主和菜单 → 点"加入白名单"（MetaMask 签名）。
- 回到助手再说一次："帮我在便利店买两瓶矿泉水和一包薯片" → 这次直接下单付款。**不用改配置，也不用重启**，因为白名单本来就在链上。
- 想展示检查的作用：把金库地址粘进去，会显示"不支持付款通知接口"，按钮是灰的。

### ⑤½ 外部平台：不用我们的合约格式也能买（x402）
- 终端先运行 `cd agent && npm run cloudeats`（模拟的外卖平台「云间外卖」）
- 助手里说"在云间外卖点个香辣鸡腿堡"：AI 拿到 HTTP 402 付款要求 → 从金库付款到平台收款地址 → 平台在链上核实 → 订单确认
- 讲解：平台不需要部署合约，只要遵循 UCP 结账 + x402 付款；额度和白名单照样由金库把关。点小票上的"付款交易"可以在 Etherscan 看到
- 控制台 → 商家白名单 → "外部平台"一栏：显示平台公布的收款地址已经核对一致
- 商家入驻页 http://localhost:5175：展示商家怎么自己开店（可选）

### ⑤¾ 平台仲裁：买家说没收到，谁来判？
- 助手里说"外卖有问题，没送到"：订单变成"申诉中"，钱冻结在商家合约托管里
- 打开 http://localhost:5176：申诉出现在列表里，展开"链上凭证"能看到每一步交易
- 用仲裁人钱包点"退款给买家" → 钱回到金库；"仲裁记录"里多一条，可以在 Etherscan 查到
- 讲解：仲裁人的权力被合约限制，只能在退款和放款之间二选一

### ⑥ 收尾：对账
- 控制台 → 链上对账：
  - 顶部三项校验：资金守恒（合计 = 存入 − 取出）、商家合约账本（余额 = 托管 + 可提现）、攻击者收到 0
  - 合计始终不变，钱只是在这几个地址之间移动
- 和演示前的截图对比：**演示前余额 − 付出去的 + 退回来的 = 演示后余额**

## 写报告用：自动生成证据文档
```bash
cd agent && npm run evidence
```
这个命令会从链上读取所有数据，生成 [`docs/EVIDENCE.md`](EVIDENCE.md)，内容包括：
- 合约地址及已验证源码的链接
- 余额对账表，以及资金守恒检查（合计 = 存入 − 取出）
- 每个订单每一步的交易、区块和实际转账
- 订单金额核对表：合约计算的金额 = 金库实际转出的金额，对应样例报告里的 Have / Result / As expected
- 审批请求
- 被拒绝的失败交易及原因

报告的"测试与验证"一节可以直接引用这份文档，再配上对账表和凭证的截图。
